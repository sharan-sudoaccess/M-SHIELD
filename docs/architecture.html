M-SHIELD · Database Architecture

Mobile Security Incident & Vulnerability Management — MySQL 8 schema mshield

A three-tier system whose integrity rules — keys, constraints, and audit logging — all live in the database layer, not the application. Below: the system tiers, the entity-relationship model, and how keys, constraints, views and triggers fit together.

3Four logical layers

A · Entity tables

The "nouns"

device, application, permission, vulnerability, analyst, incident — each a real-world thing with a surrogate AUTO_INCREMENT PK.

B · Bridge table

app_permission

Resolves the application ↔ permission many-to-many. Composite PK (app_id, permission_id) — no attributes of its own.

C · Audit table

incident_history

Append-only log. Never written by hand — triggers insert a row on every incident create and status change.

D · Derived / logic

4 views + 3 triggers

No new storage. Views package the joins; triggers automate the audit trail and resolved_at stamping.

5Integrity constraints (enforced in the data layer)

Entity integrity

PRIMARY KEY

Surrogate ids on every table; one composite PK on the bridge.

Referential integrity

FOREIGN KEY

6 relationships with CASCADE / SET NULL, all ON UPDATE CASCADE.

Domain integrity

CHECK · NOT NULL · DEFAULT

severity ∈ {Low,Medium,High,Critical}, status, priority, OS type; status defaults to Open. Cross-column check: resolved_at ≥ created_at.

Uniqueness

UNIQUE

permission.name and analyst.email can't be duplicated.

6Trigger automation (the self-maintaining audit trail)

1
INSERT incident → trg_incident_after_insert writes a CREATED row to incident_history.
2
UPDATE incident (status→Resolved/Closed) → trg_incident_before_update stamps resolved_at = NOW() before the row is saved.
3
UPDATE incident (status changed) → trg_incident_after_update logs a STATUS_CHANGE row (old → new, who, when).

7Normalization to 3NF

1NF
Atomic values — an app's permissions are individual bridge rows, never a comma-list.
2NF
The only composite key (bridge) has no non-key attributes → no partial dependencies.
3NF
No transitive dependencies — risk_level lives with permission, analyst details with analyst, audit data in its own table.
